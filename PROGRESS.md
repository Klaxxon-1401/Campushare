## 4. Feature inventory (what works)

### 4.1 Auth
- **Backend auth — built** (`api/src`): `POST /v1/auth/{register,login,verify/start,verify/confirm}`
  and `GET /v1/auth/me`. Campus-domain allowlist; scrypt password hashing; 6-digit email OTP
  (stored hashed, 10-min expiry, 60s resend cooldown, 5-attempt limit); signed JWTs carrying
  `sub / email / role / verificationStatus`. `requireAuth` / `requireVerified` / `requireAdmin`
  middleware resolve the bearer token to a verified user. In dev the OTP is also returned as
  `devCode` so the flow is testable without an inbox.
- **Authorization on resources:** items & bookings are protected. Writes require a signed-in,
  verified user, and `ownerId` / `borrowerId` are taken from the JWT — never the body. Item
  edit/delete and booking accept/decline/confirm-return are owner-only; pay/return are
  borrower-only; pickup and cancel are borrower-or-lender; reads are participant-or-admin. Draft
  listings are private to their owner. Denied access returns `403 FORBIDDEN`.
- **Email service:** `api/src/services/email.ts` — provider-agnostic; **multi-key Resend** with
  `RESEND_API_KEYS` JSON (`gmail.com` via fallback key, `student.hindustanuniv.ac.in` via dedicated
  key). **Both use `onboarding@resend.dev` as sender** — delivers to the Resend account owners
  (tested: `devanduraipragash@gmail.com` and `25cu0310065@student.hindustanuniv.ac.in` receive
  OTPs). Zero-setup dev via log driver (`setForceLogDriver(true)`). `npm run email:test` sends a
  live test; `npm run auth:smoke` covers the full auth flow.
- **Mobile app — wired:** the Auth screens call the API through `AuthContext`
  (`register → OTP → verify`, `login`, `me`); the JWT is kept in **expo-secure-store**
  (AsyncStorage fallback) and re-attached as a bearer token on launch. The navigator starts on
  `Main` when a session is restored, otherwise `Welcome`; logout clears the session. API base URL
  comes from `EXPO_PUBLIC_API_URL` (default `http://10.0.2.2:3000/v1`); cleartext HTTP is enabled
  in the manifest for the local API.

### 4.2 Listings & discovery
- Home feed with category chips, campus-verified banner, and header badges for messages + notifications.
- Search + filters (`SearchResultsScreen`), item detail with availability calendar.
- 3-step **Create Listing** wizard (details → pricing/deposit → photos) + **My Listings**
  manage screen (publish / delete drafts, edit).

### 4.3 Booking lifecycle
State machine (`src/types`): `requested → accepted → paid → active → returned`, plus
`declined`, `cancelled`, `disputed`.
- Booking request screen (date pickers, live price via `PriceSummary`, conflict handling).
- Bookings tab with borrower / lender segments; booking detail with timeline, money status,
  and per-status actions.
- Double-booking prevention at the request stage (API returns 409).

### 4.4 Payments & deposits
- Payment screen (UPI / card / wallet); rental + deposit charged on accept.
- Deposit held, shown separately everywhere, released as a refund on clean return.
- Mock payment records (`payBookingAndCharge`, `releaseDeposit`, `getPaymentsForBooking`).

### 4.5 Handover with photo evidence
- `PhotoCaptureScreen` via `expo-image-picker` (camera or gallery), timestamped + optional note.
- Evidence is **stage-locked**: “before” only during `accepted`/`paid`; “after” only while `active`.
- Handover hub: 6-step checklist, evidence list, money status, role-aware
  pickup → return → deposit-release actions. Photos gate the state transitions.

### 4.6 Messaging
- Per-booking threads (`ensureConversation`), chat screen with bubbles, unread badges on
  Home + Profile. The demo bookings ship with seeded threads; new bookings create one on demand.

### 4.7 Reviews & disputes
- Reviews: 1–5 stars + comment, only after `returned`, one review per party per booking;
  received reviews + pending-review queue.
- Disputes: reason chips, booking picker, status list (`open → under-review → resolved`);
  disputes tie back to the booking’s timestamped condition photos.

### 4.8 Notifications
- In-app notification feed (`PROJECT_PLAN §11.8`) generated on every lifecycle event: booking
  requested, request accepted/declined, payment, pickup reminder, return reminder, return
  confirmation, deposit refund, dispute updates, new messages, and reviews received.
- Bell icon with unread badge on the Home header; refresh-on-focus so badges stay current.
- `NotificationsScreen`: kind-specific icons, unread highlighting, tap-to-open the booking,
  and **Mark all read**. Seeded with activity so the feed demos immediately.

### 4.9 Admin dashboard
- `AdminScreen` (client-side): overview tiles (items, active rentals, rental revenue `₹`,

## 6. API surface (`api/src`)

- Mounted under `/v1`: `/auth`, `/items`, `/bookings`; plus `GET /health`.
- Auth: `register`, `login`, `me`, `verify/start`, `verify/confirm`.
- Items: list, get, create, update, delete, `/:id/availability`.
- Bookings: list, create, get, `accept`, `decline`, `pay`, `pickup`, `return`,
  `confirm-return`, `cancel`.
- Hardened: `helmet`, CORS allow-list, rate limiting (stricter on auth), JSON body size cap,
  flat-body parsing, centralized error handler.
- The mobile app runs against a **local in-memory store** with an identical contract
  (`mobile/src/services/api.ts` facade over `localStore.ts`) — the swap point for the network backend.

### Build environment gotchas (resolved)
1. **React Native version** — must be `0.86.3` for Expo SDK 57; `0.87.x` breaks Metro’s
   polyfill resolution. Do not bump RN independently of Expo.
2. **SDK path conflict** — `ANDROID_HOME` and `ANDROID_SDK_ROOT` must not both be set to
   different paths. Use `ANDROID_HOME=/home/devan/Android/Sdk` and unset `ANDROID_SDK_ROOT`.
3. **JDK** — the build needs **JDK 17** (`/usr/lib/jvm/java-17-openjdk`). The bundled JBR
   (Java 25) / default Java 27 trigger Gradle “Unsupported class file major version 71”.

Example local build:
```bash
cd mobile/android
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk
export ANDROID_HOME=/home/devan/Android/Sdk
unset ANDROID_SDK_ROOT
./gradlew assembleRelease --no-daemon
```

## 10. Known limitations

1. **No auth** — `CURRENT_USER` is hardcoded (`u_devan`); API stubs ids too.
2. **Mock payments** — UPI/card/wallet succeed instantly; no Stripe yet.
3. **In-memory / client-side data** — state resets on restart; `localStore` is the seed of truth.
4. **Camera on emulator** — `expo-image-picker` needs a device/emulator camera; falls back to
   the photo library.
5. **APK signing** — debug keystore; use EAS for a distributable release build.
6. **Admin console is a demo** — verification/dispute actions are client-side and session-only;
   server-side role enforcement lands with the auth milestone.
7. **Resend email delivery constraint** — only `onboarding@resend.dev` works as the sender
   (delivers to the Resend account owner). Custom `from` addresses require domain verification
   in Resend dashboard (SPF/DKIM/DMARC). Current config uses `onboarding@resend.dev` for both
   `gmail.com` (fallback key) and `student.hindustanuniv.ac.in` (dedicated key) — OTPs reach
   those inboxes because they're the account owners.
